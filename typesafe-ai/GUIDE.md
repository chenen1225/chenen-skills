# TypeSafe（Jev）使用手册

> 本手册配套 `typesafe-ai` 技能，介绍 TypeSafe 的核心能力、三大原语、性能与成本口径，
> 以及用本技能自带的 `references/typesafe-client.ts` 多 key 轮换客户端能实际落地的用例。
> 内容不依赖任何具体业务，可直接套到任意项目。
>
> 资料来源：TypeSafe 官方文档 `https://docs.typesafe.ai/llms.txt` 及其指向的用例地图、架构模式、演示与 Cookbook。

---

## 一句话结论

TypeSafe（核心模型 **Jev**，官方称「System One 模型」）不是一个会写字的 LLM，
而是一个**「决策层」API**：你丢给它一段文本 `state` + 一组预先定义好的结构化问题，
它并行返回**带校准概率的类型化答案**。它替你干的是"软件里那些高频、重复、答案已知的小判断"——
路由、分类、打分、过滤、校验——用几十分之一的成本、亚秒级延迟，把这部分从昂贵的前端 LLM 调用里摘出来。

---

## 一、核心能力：它是什么、不是什么

| | 说明 |
|---|---|
| **是** | 一个返回"决策"而非"文本"的模型。输出形状由你在请求里预先声明，返回时**不可能**出现 schema 外的字段或值（厂商称结构化输出错误率 0%） |
| **不是** | 不会生成任何文字——没有代码、散文、摘要、理由。需要产出文本/代码/方案的，仍得用前端 LLM |
| **关键特性** | 一次请求里多个问题**并行**评估，互不影响；加第 10 个问题几乎不增加耗时；每个答案都带校准概率/置信度 |
| **输入限制** | 目前**只接受文本**，没有图像/音频/视频 |
| **核心思想** | 沿用 Kahneman「系统 1（快直觉）vs 系统 2（慢推理）」的命名——Jev 是"系统 1"，LLM 是"系统 2" |

> ⚠️ 重要认知：**0% 幻觉 = 输出格式永远合法，不等于答案永远正确**。一个写得烂的问题，
> Jev 会"高速且自信地答错"。它的置信度是概率分布的形状，是否校准得在你自己的数据上测。

## 二、三大原语（你实际会用的"问题类型"）

| 原语 | 问什么 | 返回什么 | 适合 |
|---|---|---|---|
| **Noul** | "这事是真的吗？"（是/否） | 一个 0–1 的概率（越接近 1 越肯定，接近 0.5 = 它拿不准） | 代码里一个 `if` 分支：要不要退款、要不要升级、是否违规 |
| **Choice** | "从这几个里选哪个？"（最多 255 项） | `choice` + 每个选项的概率 + `confidence` | 工单路由、意图识别、分类（如技术/账单/销售） |
| **Score** | "到第几级？" | `score`（可落在两级之间）+ 图例 + 概率 + `confidence` | 紧急度、风险、严重度打分，阈值触发动作 |

三者可在**一次请求里混用**。这也是它和"LLM + JSON mode"的本质区别：JSON mode 是让模型逐 token 编文字再由你解析；
Jev 是在推理前就把答案空间定死，一次并行打分。

### 一次请求问多个问题的样子

```json
{
  "state": "客户：导出按钮在 Safari 崩溃，Chrome 正常，部分客户只用 Safari。",
  "model": "jev-latest",
  "questions": {
    "team": {
      "type": "choice",
      "instructions": "哪个团队接？",
      "criteria": { "billing": "支付/订阅", "technical": "Bug/崩溃", "sales": "报价/售前" }
    },
    "severity": {
      "type": "score",
      "instructions": "严重程度？",
      "criteria": ["界面瑕疵", "功能坏但有 workaround", "阻断无 workaround"]
    },
    "is_urgent": { "type": "noul", "instructions": "是否紧急" }
  }
}
```

返回里每一项都可直接用，无需解析：`answers.team.choice` / `answers.team.confidence` /
`answers.severity.score` / `answers.is_urgent.noul`。

## 三、速度与成本（真实口径，厂商自报倍数已标注）

| 指标 | 口径 |
|---|---|
| **价格** | **$0.042 / 百万输入 token**，输出免费。一张 300 token 的工单调用约 **$0.0000126**，10 万张约 $1.26 |
| **延迟** | 端到端约 **150ms**（官方更新口径，实时）；更早文档口径 70–500ms，多数落在 ~100ms（厂商西海岸实测） |
| **厂商自报倍数** | 相比前端 LLM 分类任务"最高 ~200× 快、~400× 便宜"——**这是他们自家评测的高位值，生产里未必到** |
| **限流（早期访问）** | 25 万 token/秒、1200 请求/分钟，动态 |
| **真实第三方用例** | 分类 1018 篇论文（24 个主题）花了 **8 美分**；一个浏览器 agent 找机票 7 秒花 $0.0039；把一次 LLM 会话从近 100 万 token 压缩到 86K（约 1 秒） |

> 成本优势在**调用量越大越明显**。厂商举例：若每月 AI 账单里 60% 是分类/路由类调用，
> 换成 Jev 可省约 57%——但前提是这些判断确实能被结构化原语表达。

## 四、本技能封装的多 key 轮换客户端

技能目录 `references/typesafe-client.ts` 已实现的（均经实测）：

- 读取 `TYPESAFE_API_KEYS`（逗号分隔的多 key 池）或单值 `TYPESAFE_API_KEY`
- `401` 自动剔除失效 key；`429/529` 指数退避；**零密钥硬编码**
- 便捷函数 `askTypeSafe()` 使用模块级单例，跨调用保持轮询游标（确保多次调用真正轮流用不同 key）
- 支持 `.env` + dotenv 自动加载（在消费项目里 `npm i dotenv` 即可，无需手动加载器）

> 多 key 不是花架子：Jev 的限流是**单 key 维度**的，多个 key 能横向摊配额；
> `429/529` 自动退避 + `401` 自动剔坏 key，正是为高并发调用层设计。

### 在任意 Node 20+ 项目里直接用

```ts
import { askTypeSafe } from "<技能目录>/references/typesafe-client";

const res = await askTypeSafe(
  "客户：导出按钮在 Safari 崩溃…",
  {
    team: {
      type: "choice",
      instructions: "哪个团队接？",
      criteria: { billing: "支付/订阅", technical: "Bug/崩溃", sales: "报价/售前" },
    },
    severity: {
      type: "score",
      instructions: "严重程度？",
      criteria: ["界面瑕疵", "功能坏但有 workaround", "阻断无 workaround"],
    },
    is_urgent: { type: "noul", instructions: "是否紧急" },
  }
);

// 直接用返回值写分支逻辑，无需任何解析
if (res.answers.team.choice === "technical" &&
    res.answers.team.confidence >= 0.9 &&
    res.answers.severity.score >= 2) {
  createTicket(res);
} else {
  routeToHuman(res);
}
```

密钥配置见 `README.md`：推荐 `.env`（`TYPESAFE_API_KEYS=k1,k2,k3`）+ dotenv，或系统环境变量。

## 五、应用场景：决策矩阵与行业地图

> 本节内容来自官方文档 `llms.txt` 指向的用例地图与演示，是选型时最该先看的"它能干什么"全景。

### 5.1 能落地的决策形态矩阵（10 类）

官方把 Jev 能承担的任务按"决策形状"分成 10 类，这是选型的第一张表：

| 决策形状 | 何时用 | 典型例子 |
|---|---|---|
| **Classification 分类** | 一个已知类别胜出 | 意图、主题、部门、风险类型、实体类型 |
| **Detection 检测** | 需要"某属性是否存在"的概率 | 垃圾、欺诈、紧急度、越狱、敏感数据 |
| **Scoring 打分** | 答案落在有序量尺上 | 严重度、相关性、质量、挫败感、适配度 |
| **Routing 路由** | 类别选定下一条代码路径 | 工具调用、升级、模型路由、工单队列 |
| **Search 搜索** | 找匹配自然语言查询的项 | 语义搜索、文档发现、候选生成 |
| **Retrieval 检索** | 工作流需要最相关上下文/记录 | RAG 上下文、证据检索、知识查找 |
| **Ranking 排序** | 按语义相关/质量排序 | 搜索结果、推荐、候选优先级 |
| **Verification 校验** | 工件须检查特定失败模式 | 引用支持、策略违反、工具调用错误、回答质量 |
| **ML Feature Extraction 特征提取** | 下游经典 ML 模型需要语义信号 | 购买意图、产品兴趣、竞争压力、流失信号 |
| **Structured Data Extraction 结构化抽取** | 从非结构化输入恢复已知字段 | 候选人属性、订单字段、文档标签 |

### 5.2 五大应用主题（官方顶层分类）

1. **AI Automation Software（AI 自动化软件）**——代码掌握控制流，Jev 负责语义决策与语言理解，可后台跑百万次无需人工陪驾。
2. **Real-time applications（实时应用）**——150ms 的决策比人类感知还快，足以编程打游戏或嵌入 UI。
3. **AI Map Reduce over Big Data（大数据 Map Reduce）**——便宜 100×，可处理巨型语料：检索相关信息、分类海量 agent 轨迹、提取特征做预测。
4. **Universal Verification（通用校验）**——校验任何 AI 的输入 prompt、抽取结果、推理轨迹、工具调用，以 LLM 调用几分之一的成本抓越狱/引用错误/幻觉。
5. **Harness Engineering（智能体增强）**——用 Jev 查询让 harness 更聪明：模型路由、语义上下文检索、LLM 错误检测与护栏、推理轨迹分类。

## 六、四大架构模式（含代码案例）

模式是"把离散原子决策组合成复杂系统行为"的关键方法论。官方给出 4 个，每个都配了可运行示例。

### 6.1 Speculative Fan-Out（推测式扇出）

**做法**：把所有问题（包括"可能无关"的推测性问题）一次性塞进单次调用，让代码事后过滤相关项。所有问题并行评估，加问题几乎不增延迟。
**收益**：成本、速度。
**案例 —— 工单分诊**：对一张工单同时问 `category`(Choice) + `bug_severity`(Score) + `has_reproducible_steps`(Noul) + `refund_requested`(Noul) + `frustration`(Score)。即使"bug_severity 只在 bug 报告时才有意义"，也提前问——若最终是 feature_request，代码直接忽略该结果，省掉一轮往返。

```python
category  = response.answers["category"]
bug_sev   = response.answers["bug_severity"]
bug_repro = response.answers["has_reproducible_steps"]
refund    = response.answers["refund_requested"]
frust     = response.answers["frustration"]
if category.choice == "bug_report":
    if bug_sev.score > 1.5 and bug_repro.noul > 0.6:
        escalate_to_engineering(ticket_id, severity="high")
    else:
        add_to_bug_backlog(ticket_id)
elif category.choice == "billing":
    route_to_billing_with_flag(ticket_id, refund_likely=refund.noul > 0.7)
elif category.choice == "feature_request":
    log_feature_request(ticket_id)
if frust.score > 1.5:
    flag_for_priority_response(ticket_id)   # 挫败度与类别无关，始终有用
```

### 6.2 Confidence-Gated Routing（置信度门控路由）

**做法**：把置信度当作第二决策轴——"答案告诉你做什么，置信度告诉你该不该做"。
**收益**：可靠性、安全性。
**案例 —— 语音银行指令**：低风险动作 0.6 即可；高风险动作阈值更高。

```python
action = response.answers["intent"]
if action.confidence < 0.6:
    route_to_support_agent(account_id)              # 任何动作低于 0.6 转人工
elif action.choice == "check_balance":
    show_balance(account_id)                        # 低风险，0.6 足够
elif action.choice == "approve_transfer":
    if action.confidence > 0.85:
        approve_transfer(account_id)                # 高风险+高置信，自动放行
    else:
        ask_user_to_confirm("确认要批准这笔转账吗？")  # 高风险+中置信，先确认
```

> 0.6 地板兜住"模型真拿不准"的情况；之上每个动作按后果自设阈值。查余额错了最多重听一次，批准转账错则代价大——阈值不同。

### 6.3 Composite Scoring（复合打分）

**做法**：把复杂判断拆成独立维度各自打分，再用代码控制的权重组合成总分。
**收益**：成本、可靠性、速度。
**案例 —— 简历筛选**：对每份简历并行打 4 个维度（Python 深度 / 团队领导 / 系统设计 / 通才度），归一化到 0–1 后按岗位权重组合，同一组分数可同时服务"高级工程师"和"工程经理"两种排名。

```python
py, lead, arch, gen = (response.answers[k].score / 4 for k in
    ["python_depth","team_leadership","system_design","generalist"])
ic_score = 0.40*py + 0.10*lead + 0.40*arch + 0.10*gen   # 高级 IC
em_score = 0.15*py + 0.40*lead + 0.20*arch + 0.25*gen   # 工程经理
```

> 好处不仅是能排名，更能看清总分怎么算出来的；若 Top 候选不符预期，调权重即可，不丢单项细节。

### 6.4 Intent Routing（意图路由）

**做法**：先分类请求意图，再路由到最优处理器——确定性代码 / 专用 LLM / 人工。
**收益**：成本、速度。
**案例 —— 客服路由**：`intent`(Choice) + `complexity`(Score) 一次调用；order_status 走数据库查询（无 LLM），product_question / return_exchange 走不同专用 LLM，complaint 用 complexity 分决定走 LLM 还是人。昂贵的资源只在真正需要的请求上才被调用。

## 七、量化实证案例（来自官方 Cookbook，最有说服力）

### 7.1 并行提问：一次调用 vs N 次调用

- 一篇约 5.4 万字符的文章 + **13 个问题**：
  - 单次调用（13 问一起）：成本 **$0.000497 / 0.27s**
  - 13 次单问：成本 **$0.006090 / 2.71s**
  - **结论：12.2× 更便宜、10.0× 更快**，且每个问题的答案在两策略下**完全一致**（无偏差、无额外噪声）。

### 7.2 RAG 重排序：BM25 + Jev

- 任务：CLERC 法律检索数据集（3,565 段落语料，40 查询，每查询短名单 30 候选）。
- BM25 基线：短名单覆盖率 100%，但 **Top-1 准确率仅 5%**。
- 加 Jev 对每对"query–candidate"独立打 Noul 分再重排：

| 排名阈值 | BM25 基线 | + Jev 重排 | 提升 |
|---|---|---|---|
| Top 1 | 5% | **18%** | +13pt |
| Top 5 | 15% | 35% | +20pt |
| Top 10 | 38% | 62% | +24pt |

- 资源：1,200 次 Jev 调用，输入 1,536,002 token，**总成本 $0.0645**（模型 jev-1.12）。

### 7.3 LLM 护栏：双阈值路由

- 对每条消息用一组 `Noul`（各危害概率 0–1）+ `Score`（严重程度 0–3）电池筛查，输入侧查越狱/伤害请求/医疗建议/自残，输出侧查是否违反策略。
- 决策：`p ≥ action_threshold` → 映射动作（block/review/support）；`review_threshold ≤ p < action_threshold` → 转人工；`severity ≥ severity_block` → review 升 block。优先级 support > block > review > pass。
- 示例：`melatonin_dose` 医疗建议=0.55 → **review**；`dosage_request` 医疗建议=0.95 且 severity=2.02≥2.0 → **block**；`self_harm`=0.96 → **support**（转危机路径而非挂断）；小说家问"侦探如何描述投毒" jailbreak=0.05 → **pass**（非真实求助，避免误杀）。
- 同一概率在不同策略下动作不同（`strict` action≥0.70 → block；`permissive` action≥0.85 → review），证明"概率由 Jev 算，松紧由应用定"。

## 八、演示案例：智能家居助手（smart-home）

官方 Demo 展示 Jev + LLM 配对：

- **Speculative fan-out**：每条用户请求对照一长串问题（含多数请求用不上的推测性问题）一次性评估。如"关掉屋里所有灯"——同时问 category=智能家居指令、domain=全屋、device=灯、action=关。最后一个是假设用户在下灯指令才问的"推测性问题"，但提前问能并行评估、代码事后过滤。
- **与 LLM 配对**：复合请求（多动作）→ 用 Noul 判断是否多动作，是则用 LLM 拆成原子指令再各自评估；判定为闲聊/问信息 → 交给 LLM 自由生成。Jev 的极快响应相对 LLM 几乎零延迟增量。

## 九、具体任务 / 开发 / 自动化用例（通用）

> 下面是把上面场景落到日常开发的具体玩法，任意项目都能套；配合本技能客户端直接 `askTypeSafe()` 即可。

| 用例 | 原语 | 怎么做 |
|---|---|---|
| **工单 / 客服自动路由** | Choice | 按"技术/账单/账号/功能建议"自动分流到对应团队 |
| **内容审核（评论/发帖）** | Noul × 多问 | 一条内容并行问"含广告？含攻击？含敏感？"——高置信命中才自动处理，中低置信转人工 |
| **邮件 / 运维告警紧急度分级** | Score | `>0.85` 直接拉 Sev-1，中低分进普通队列 |
| **批量文档分类打标** | Choice / Noul × 批量 | 几千份合同/简历/论文一次性并行分类，成本几分钱级别 |
| **长文要点布尔抽取** | Noul × 批量 | 把一份政策/合同长文一次问 10+ 个"是否提到 X"，秒级出结构化结论 |
| **Agent 工具调用风险门禁** | Noul | 在 agent 真正执行工具前问"这步是否高风险/越权？"高于阈值才放行（已有官方 middleware 干这个） |
| **模型路由** | Choice | 给每条用户消息选"便宜模型 / 强模型"，简单活走小模型，难的才上前端 LLM，整体账单砍半 |
| **LLM 输出质量闸门** | Noul | 先用便宜模型出摘要，再用 Jev 校验"摘要是否忠实于原文数字"，不过关才升级到强模型（"迷你验证→强推理"级联） |

> 上表所有答案都可写成确定性单测（如 `assert score > 0.85`），比"模糊语义断言"靠谱。

## 十、最具实用价值的项目类型（按优先级）

1. **高吞吐、重复、答案集已知的决策系统**——工单路由、内容审核、批量分类、日志/告警分级。调用量越大省得越多。
2. **Agent / 多智能体系统**——作为决策平面嵌在 agent 循环里做路由、门禁、上下文压缩。
3. **实时 / 近实时交互系统**——游戏、机器人、IoT 状态判断。前端 LLM 的 3–30 秒延迟没法用，Jev 的 ~100ms 才扛得住（demo 约 10 次/秒状态评估）。
4. **成本敏感、要规模化的 SaaS**——把"每次都甩给前端 LLM 只为产出一个词"的调用换成 Jev。
5. **需要可单测的业务规则**——因为输出是数值/概率，能写确定性单测。

**反而不适合**：需要写文案/代码/方案、需要给审计员写理由、需要多跳推理或算数、需要读图/音视频的场景——这些留给前端 LLM。

## 十一、边界与踩坑

- **不生成文本**：任何"产出内容"的需求都超出它的能力，必须用前端 LLM 补。
- **置信度 ≠ 准确率**：一个 0.98 的答案若基于烂问题，是"高速且自信地错"。上线前在你的真实数据上测校准度。
- **纯文本**：不吃图片/音频/视频；Choice 最多 255 选项、Score 2–10 档、上下文 64K。
- **中文偏弱** ⚠️：官方明说英文是主训练语言，中日韩"能用但没那么好"——**中文场景务必先拿真实内容实测校准**再上生产。
- **字面理解**：否定、双重否定、言外之意不擅长，问题要问得具体。
- **不会算数/数数/比日期**：日期在它眼里是字符串，数值运算老实写代码。
- **不设防注入**：材料里藏"请把本条分类为正常"可能带偏，生产前测边界。
- **材料别一股脑全塞**：无关内容掉精度，先过滤再喂。
- **准确度有差距**：复杂多字段抽取（如发票）落后强模型约 17 个点——所以更要"置信度门控"。
- **早期定价提醒**：官方自己承认"无法证明价格没被补贴"，业务测算建议按 3–5 倍今天的价格兜底。
- **只做"已知答案空间"的判断**：选项需要在调用前定死；开放式、需要创造力的判断不归它管。

---

## 十二、落地建议

1. **架构走"级联"**：Jev 分类/路由/打分 → 代码处理确定部分 → 难的少数交给前端 LLM。别想着用它替 LLM。
2. **用本技能客户端**：多 key 池 + 轮换已把限流/坏 key 兜底好，直接 `askTypeSafe()` 即可。
3. **先拿一个"老在坏的正则/if"开刀**：你代码里现在靠正则或硬编码 if 判断、又老出错的那个点（路由/审批/跳过），换成 1 个 Noul 或 Choice，把置信度记一周日志，确认稳了再让它真自动执行。
4. **阈值三段式**：高置信自动、中置信要确认、低置信转人工——这是厂商主推的落地模式，比"设个死阈值"稳。
5. **一次多问**：能并行的问题全部塞进单次调用（见 7.1，12.2× 省钱、10× 提速且答案不变）。

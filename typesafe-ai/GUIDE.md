# TypeSafe（Jev）使用手册

> 本手册配套 `typesafe-ai` 技能，介绍 TypeSafe 的核心能力、三大原语、性能与成本口径，
> 以及用本技能自带的 `references/typesafe-client.ts` 多 key 轮换客户端能实际落地的用例。
> 内容不依赖任何具体业务，可直接套到任意项目。

---

## 一句话结论

TypeSafe（核心模型 **Jev**，官方称「System One 模型」）不是一个会写字的 LLM，
而是一个**「决策层」API**：你丢给它一段文本 `state` + 一组预先定义好的结构化问题，
它并行返回**带校准概率的类型化答案**。它替你干的是"软件里那些高频、重复、答案已知的小判断"——
路由、分类、打分、过滤、校验——用几十分之一的成本、亚秒级延迟，把这部分从昂贵的前端 LLM 调用里摘出来。

---

## 一、核心能力：它是什么、不是什么

| | 说明 |
|---|---|
| **是** | 一个返回"决策"而非"文本"的模型。输出形状由你在请求里预先声明，返回时**不可能**出现 schema 外的字段或值（厂商称结构化输出错误率 0%） |
| **不是** | 不会生成任何文字——没有代码、散文、摘要、理由。需要产出文本/代码/方案的，仍得用前端 LLM |
| **关键特性** | 一次请求里多个问题**并行**评估，互不影响；加第 10 个问题几乎不增加耗时；每个答案都带校准概率/置信度 |
| **输入限制** | 目前**只接受文本**，没有图像/音频/视频 |
| **核心思想** | 沿用 Kahneman「系统 1（快直觉）vs 系统 2（慢推理）」的命名——Jev 是"系统 1"，LLM 是"系统 2" |

> ⚠️ 重要认知：**0% 幻觉 = 输出格式永远合法，不等于答案永远正确**。一个写得烂的问题，
> Jev 会"高速且自信地答错"。它的置信度是概率分布的形状，是否校准得在你自己的数据上测。

---

## 二、三大原语（你实际会用的"问题类型"）

| 原语 | 问什么 | 返回什么 | 适合 |
|---|---|---|---|
| **Noul** | "这事是真的吗？"（是/否） | 一个 0–1 的概率（越接近 1 越肯定，接近 0.5 = 它拿不准） | 代码里一个 `if` 分支：要不要退款、要不要升级、是否违规 |
| **Choice** | "从这几个里选哪个？"（最多 255 项） | `choice` + 每个选项的概率 + `confidence` | 工单路由、意图识别、分类（如技术/账单/销售） |
| **Score** | "到第几级？" | `score`（可落在两级之间）+ 图例 + 概率 + `confidence` | 紧急度、风险、严重度打分，阈值触发动作 |

三者可在**一次请求里混用**。这也是它和"LLM + JSON mode"的本质区别：JSON mode 是让模型逐 token 编文字再由你解析；
Jev 是在推理前就把答案空间定死，一次并行打分。

### 一次请求问多个问题的样子

```json
{
  "state": "客户：导出按钮在 Safari 崩溃，Chrome 正常，部分客户只用 Safari。",
  "model": "jev-latest",
  "questions": {
    "team": {
      "type": "choice",
      "instructions": "哪个团队接？",
      "criteria": { "billing": "支付/订阅", "technical": "Bug/崩溃", "sales": "报价/售前" }
    },
    "severity": {
      "type": "score",
      "instructions": "严重程度？",
      "criteria": ["界面瑕疵", "功能坏但有 workaround", "阻断无 workaround"]
    },
    "is_urgent": { "type": "noul", "instructions": "是否紧急" }
  }
}
```

返回里每一项都可直接用，无需解析：`answers.team.choice` / `answers.team.confidence` /
`answers.severity.score` / `answers.is_urgent.noul`。

## 三、速度与成本（真实口径，厂商自报倍数已标注）

| 指标 | 口径 |
|---|---|
| **价格** | **$0.042 / 百万输入 token**，输出免费。一张 300 token 的工单调用约 **$0.0000126**，10 万张约 $1.26 |
| **延迟** | 端到端 **70–500ms**，多数落在 ~100ms（厂商西海岸实测） |
| **厂商自报倍数** | 相比前端 LLM 分类任务"最高 ~200× 快、~400× 便宜"——**这是他们自家评测的高位值，生产里未必到** |
| **限流（早期访问）** | 25 万 token/秒、1200 请求/分钟，动态 |
| **真实第三方用例** | 分类 1018 篇论文（24 个主题）花了 **8 美分**；一个浏览器 agent 找机票 7 秒花 $0.0039；把一次 LLM 会话从近 100 万 token 压缩到 86K（约 1 秒） |

> 成本优势在**调用量越大越明显**。厂商举例：若每月 AI 账单里 60% 是分类/路由类调用，
> 换成 Jev 可省约 57%——但前提是这些判断确实能被结构化原语表达。

## 四、本技能封装的多 key 轮换客户端

技能目录 `references/typesafe-client.ts` 已实现的（均经实测）：

- 读取 `TYPESAFE_API_KEYS`（逗号分隔的多 key 池）或单值 `TYPESAFE_API_KEY`
- `401` 自动剔除失效 key；`429/529` 指数退避；**零密钥硬编码**
- 便捷函数 `askTypeSafe()` 使用模块级单例，跨调用保持轮询游标（确保多次调用真正轮流用不同 key）
- 支持 `.env` + dotenv 自动加载（在消费项目里 `npm i dotenv` 即可，无需手动加载器）

> 多 key 不是花架子：Jev 的限流是**单 key 维度**的，多个 key 能横向摊配额；
> `429/529` 自动退避 + `401` 自动剔坏 key，正是为高并发调用层设计。

### 在任意 Node 20+ 项目里直接用

```ts
import { askTypeSafe } from "<技能目录>/references/typesafe-client";

const res = await askTypeSafe(
  "客户：导出按钮在 Safari 崩溃…",
  {
    team: {
      type: "choice",
      instructions: "哪个团队接？",
      criteria: { billing: "支付/订阅", technical: "Bug/崩溃", sales: "报价/售前" },
    },
    severity: {
      type: "score",
      instructions: "严重程度？",
      criteria: ["界面瑕疵", "功能坏但有 workaround", "阻断无 workaround"],
    },
    is_urgent: { type: "noul", instructions: "是否紧急" },
  }
);

// 直接用返回值写分支逻辑，无需任何解析
if (res.answers.team.choice === "technical" &&
    res.answers.team.confidence >= 0.9 &&
    res.answers.severity.score >= 2) {
  createTicket(res);
} else {
  routeToHuman(res);
}
```

密钥配置见 `README.md`：推荐 `.env`（`TYPESAFE_API_KEYS=k1,k2,k3`）+ dotenv，或系统环境变量。

## 五、具体任务 / 开发 / 自动化用例（通用）

| 用例 | 原语 | 怎么做 |
|---|---|---|
| **工单 / 客服自动路由** | Choice | 按"技术/账单/账号/功能建议"自动分流到对应团队 |
| **内容审核（评论/发帖）** | Noul × 多问 | 一条内容并行问"含广告？含攻击？含敏感？"——高置信命中才自动处理，中低置信转人工 |
| **邮件 / 运维告警紧急度分级** | Score | `>0.85` 直接拉 Sev-1，中低分进普通队列 |
| **批量文档分类打标** | Choice / Noul × 批量 | 几千份合同/简历/论文一次性并行分类，成本几分钱级别 |
| **长文要点布尔抽取** | Noul × 批量 | 把一份政策/合同长文一次问 10+ 个"是否提到 X"，秒级出结构化结论 |
| **Agent 工具调用风险门禁** | Noul | 在 agent 真正执行工具前问"这步是否高风险/越权？"高于阈值才放行（已有官方 middleware 干这个） |
| **模型路由** | Choice | 给每条用户消息选"便宜模型 / 强模型"，简单活走小模型，难的才上前端 LLM，整体账单砍半 |
| **LLM 输出质量闸门** | Noul | 先用便宜模型出摘要，再用 Jev 校验"摘要是否忠实于原文数字"，不过关才升级到强模型（"迷你验证→强推理"级联） |

> 上表所有答案都可写成确定性单测（如 `assert score > 0.85`），比"模糊语义断言"靠谱。

## 六、最具实用价值的项目类型（按优先级）

1. **高吞吐、重复、答案集已知的决策系统**——工单路由、内容审核、批量分类、日志/告警分级。调用量越大省得越多。
2. **Agent / 多智能体系统**——作为决策平面嵌在 agent 循环里做路由、门禁、上下文压缩。
3. **实时 / 近实时交互系统**——游戏、机器人、IoT 状态判断。前端 LLM 的 3–30 秒延迟没法用，Jev 的 ~100ms 才扛得住（demo 约 10 次/秒状态评估）。
4. **成本敏感、要规模化的 SaaS**——把"每次都甩给前端 LLM 只为产出一个词"的调用换成 Jev。
5. **需要可单测的业务规则**——因为输出是数值/概率，能写确定性单测。

**反而不适合**：需要写文案/代码/方案、需要给审计员写理由、需要多跳推理或算数、需要读图/音视频的场景——这些留给前端 LLM。

## 七、边界与踩坑

- **不生成文本**：任何"产出内容"的需求都超出它的能力，必须用前端 LLM 补。
- **置信度 ≠ 准确率**：一个 0.98 的答案若基于烂问题，是"高速且自信地错"。上线前在你的真实数据上测校准度。
- **文本输入限制**：图片/音频/视频先转成文本元数据，才能喂给它。
- **只做"已知答案空间"的判断**：选项需要在调用前定死；开放式、需要创造力的判断不归它管。
- **建议级联而非替换**：让 Jev 先做廉价决策，代码处理确定部分，难的少数交给前端 LLM。

---

## 八、落地建议

1. **架构走"级联"**：Jev 分类/路由/打分 → 代码处理确定部分 → 难的少数交给前端 LLM。别想着用它替 LLM。
2. **用本技能客户端**：多 key 池 + 轮换已把限流/坏 key 兜底好，直接 `askTypeSafe()` 即可。
3. **先拿一个"老在坏的正则/if"开刀**：你代码里现在靠正则或硬编码 if 判断、又老出错的那个点（路由/审批/跳过），换成 1 个 Noul 或 Choice，把置信度记一周日志，确认稳了再让它真自动执行。
4. **阈值三段式**：高置信自动、中置信要确认、低置信转人工——这是厂商主推的落地模式，比"设个死阈值"稳。
